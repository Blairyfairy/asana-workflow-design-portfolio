# Phoenix Airlines Asana Conventions

Version: 1.0 | Owner: Workflow Owner (role placeholder) | Review cadence: Quarterly

## Project naming
Use `Business Area — Outcome or Workflow — YYYY` when a year is useful. Avoid vague names such as “New Project” or “Misc.”

## Task naming
Start with a clear action verb: Define, Review, Approve, Validate, Publish, Notify, Measure, or Resolve. Name the deliverable, not just the activity.

**Preferred:** `Validate accessibility and fallback scenarios`  
**Avoid:** `Accessibility`

## Task descriptions
Each description should state:
1. Purpose / context.
2. Deliverable.
3. Acceptance criteria.
4. Required collaborators or reviewers.
5. Evidence location (never sensitive data).
6. Escalation route for blockers.

## Ownership
- Every active task has one accountable assignee.
- Add collaborators for consultation, not as a substitute for an owner.
- Reassign tasks when ownership changes; document the handoff.

## Due dates
- Use the project calendar and agreed working days.
- A due date is a commitment, not a guess.
- If the date changes, update it and communicate the reason when material.

## Sections and statuses
- Sections describe meaningful workflow phases or states.
- Do not create a new section for every person.
- Use “Needs Information” rather than leaving incomplete requests silently in triage.
- Use “Declined / Withdrawn” for closed requests that will not proceed.

## Custom fields
- Use approved options and definitions.
- Do not invent new option labels ad hoc.
- Keep free text for context, not values intended for reporting.
- Review fields quarterly and retire unused fields with the workflow owner.

## Comments, attachments, and links
- Put decisions and handoff context in the task.
- Link to the approved document location.
- Do not attach passenger records, biometric data, credentials, or restricted security information to general workflow tasks.

## Approvals
- Record the approver, decision, date, and rationale or evidence link.
- Never use a status change alone as a substitute for required governance approval.
- Critical urgency triggers faster review, not automatic approval.

## Rules and notifications
- Every rule must have a clear trigger, condition, and action.
- Avoid duplicate notifications and loops.
- Test with a non-production project before enabling organization-wide.
- Assign an owner to monitor rule failures.

## Archiving and maintenance
- Close or archive completed projects according to retention policy.
- Review stale requests and inactive projects monthly.
- Workflow owner reviews fields, rules, goals, and conventions quarterly.
